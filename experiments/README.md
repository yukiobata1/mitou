# 実験メモ：公開シミュレータ U-FAST の試用

- 作成: 2026-09-21（Claudeによる試用の記録。数値の妥当性は未検証）
- 目的: 応募前の最小デモの土台にできるかの確認。担当候補: 松川

## U-FAST とは

- https://github.com/DaeeunLim/ufast （MITライセンス、Python 3.10以上、江原大学校 Dae-Eun Lim）
- 半導体工場の生産（SMT2020データ）とOHT搬送を同じ時計で動かす共同シミュレーション。搬送だけを回すモードもある
- 同梱データ: `dataset/case1.rail`（ノード296、リンク350、装置100の小さなレール網）、`dataset/SMAT2022.rail`（READMEによれば実工場由来のレイアウト）、生産データ HVLM / LVHM / LVLM、台車仕様 `vehicle_spec.json`
- 実装済み: 最短経路、渋滞に反応する動的経路（`--routing dynamic`）、台車の割当4種（`--strategy fifo|nearest|same_section|congestion`）、渋滞モデル4種、デッドロック検出
- 自作の経路選択・割当・経路コストをプラグインとして差し込める（`--custom-routing` など。雛形は `examples/`）
- 公開直後のコード（コミット9件、利用実績なし）。**数値を申請書に使う前に、指標の定義をコードで確認すること**

## 動かし方（Windowsでの注意つき）

```bash
cd experiments
git clone --depth 1 https://github.com/DaeeunLim/ufast.git
python -m venv .venv
.venv/Scripts/python -m pip install --default-timeout 180 -e ./ufast   # 依存は numpy, pandas, scipy など

# 日本語Windowsでは必須。無いと結果表示で UnicodeEncodeError (cp932) になり止まる
export PYTHONUTF8=1 PYTHONIOENCODING=utf-8

cd ufast
../.venv/Scripts/ufast-fromto dataset/case1.rail dataset/case1_Fromto.dat --oht 50 --duration 3600
```

- 搬送だけのモードは、1時間分が実時間6〜12秒で終わる
- 需要を倍率で変えるフラグは無い。需要表（タブ区切り: 出発装置、到着装置、1時間あたり件数）の3列目を掛け算して別ファイルを作る:
  `awk -v k=20 'BEGIN{FS=OFS="\t"} {$3=$3*k; print}' dataset/case1_Fromto.dat > sweep/fromto_x20.dat`
- 既定の需要は薄い（50台で稼働率6.5%、渋滞ほぼなし）。10倍で稼働率71%、20倍で91%となり、ブロッキングがはっきり出る

## 試用で見えた不審点（要確認）

1. 平均搬送時間が数秒（8.2秒など）。実際のOHT搬送は分単位。case1のレイアウト寸法が現実と違うか、指標の定義が想定と違う可能性
2. 需要を変えただけで「渋滞なしの搬送時間（free-flow）」が 8.1秒 → 4.8秒 → 2.5秒 と変わる。需要の倍率で出発・到着の組の構成が変わるのか、集計方法の問題かは未確認
3. `SMAT2022.rail` と生産つきの共同シミュレーション（`ufast-run`）は未試用

## 最小デモでやりたいこと

1. 台数を変えたときの搬送量・搬送時間の曲線（メーカー技術者の2007年の記述「過度の増車は逆に搬送能力を低下させる」の再現になるか）
2. 最短経路、動的経路、公開論文のQ-routingの再現実装、提案方式の同条件比較
3. 生産つきのモードで、渋滞が完成までの日数と装置の稼働に効くかの測定（「搬送は律速か」という問いへの答え）
4. 図2枚と画面録画1〜2分。申請書には「公開シミュレータ上の結果」であることを明記する

U-FASTが使いものにならなければ、自作の小さなレール網に切り替える。

## 提案手法の予備実装（2026-09-22 夜）

独立批評（research/audit-2026-09-22.md）の指摘を受けて、次の3点を直した実験を回している。

1. **ポアソン到着**: `run_mc.py` が `generate_fixed_interval_events` を指数分布の到着間隔に差し替える（U-FAST本体は変更しない）
2. **提案手法（限界費用コスト）を実装**: `--method mc`。区間の出入り（`amhs._add_inflight/_remove_inflight`）を包んで、区間ごとの実測通過時間のEWMAと最小値（自由走行の代理）を持つ。辺コスト = 自由走行時間 × (1 + β·(実測 − 自由走行)/自由走行)、β = 1+p（多項式遅れ d = t0 + a·nᵖ で n·d′ = p·(d − t0)。p=1 → β=2）。台数の傾き推定は要らない（Δ-tolling型）。比較対象の内蔵動的経路は「台数比例の固定重み」
3. **狙う領域**: 需要40倍（25台では足りない）で台数20〜80を振り、稼働率が85〜100%の帯を見る。指標は完了件数、平均配送時間、配送時間の95パーセンタイル、稼働率

- 実行: `bash mc_sweep.sh`（台数6 × 手法3 × 種3 = 54本。mcは純Pythonの経路探索になるため1本約6.5分。全体で3〜4時間）
- 結果: `mc-sweep-2026-09-22.txt`（1行1本のJSON）。48本目でメモリ逼迫のため停止（種0・1は全条件、種2は50台の動的経路まで）。集計と図は `plot_mc_sweep.py` → `fig-mc-sweep-2026-09-22.png`

### 結果（2026-09-22 夜、需要40倍、ポアソン到着、1時間、種2〜3の平均）

| 台数 | 静的: 完了／p95[s] | 内蔵動的: 完了／p95 | 提案(β=2): 完了／p95 |
|---|---|---|---|
| 20 | 36,210 / 1,219 | 35,995 / 1,249 | 35,901 / 1,245 |
| 30 | 39,578 / 1,004 | 44,051 / 752 | 43,828 / 771 |
| 40 | 40,505 / 983 | 46,873 / 604 | 45,496 / 688 |
| 50 | 36,413 / 889（デッドロック6.7） | 47,514 / 568 | 45,374 / 714 |
| 60 | 29,624 / 725（18.0） | 46,561 / 623 | 45,432 / 713 |
| 80 | 17,469 / 1,637（36.5） | 43,637 / 783（3.0） | 42,906 / 834（0） |

読み:

1. **ポアソン到着で「増やすと崩れる」曲線が出た。** 静的最短経路は50台からデッドロックが増え、80台で完了件数が半減。内蔵動的経路は80台まで持つ。B4とG3の予備的な裏付けとして使える（小規模網である注記つき）
2. **提案手法の初版は、内蔵の動的経路（台数比例の固定重み）に勝っていない。** 20〜30台では同等、40〜60台ではp95で10〜25%劣る。80台ではデッドロック0（内蔵は3）で完了件数は同等。専門家批評が予測した「原理のない固定重みで9割取れる」状態そのもの
3. 考えられる原因（未検証）: (a) 区間の自由走行時間の代理に「最小観測値」を使っており、低すぎる値で遅れが過大評価される。(b) EWMA（α=0.3）が遅れの変化に遅れる。(c) 区間の遅れを辺に比例配分しているが、遅れは合流点で発生する（批評の指摘）。(d) β=2 は未調整。(e) 内蔵の動的経路はコストに上限（cap 3.0）があり振動しにくいが、提案手法には上限がない
4. **申請書での扱い**: 「公開シミュレータ上で提案手法の予備実装を行い、先行方式と同条件で比較中」と書く。図は静的 vs 動的の曲線（1の結果）を使い、提案手法の線は載せない。二次審査までに (a)(c)(e) を直して再実験する

次にやること（優先順）: (e) コストに上限を入れる → (a) 自由走行時間を区間の物理長と速度から計算する → (c) 課金の単位を合流点に移す → βを {1, 2, 4} で振る
- 注意: case1のレールは座標がmm単位で全体が約30m四方の小さな網。搬送時間が数秒なのは単位の不整合ではなく、レイアウトが小さいため。実工場規模は `dataset/SMAT2022.rail` だが、対応する需要表が同梱されていない

## 実工場規模（SMAT2022.rail、300m×150m、ノード2,858）での試走（2026-09-22 夜）

- 需要表は同梱されていないので `make_smat_fromto.py` で合成: `transport_times_between_tool_groups.csv` の装置群ペア11,556本に、n_eq(from)×n_eq(to) の重みで総量（件/時）を配分。`sweep/smat_fromto_{4000,8000,30000}.dat`
- 平均搬送時間は42〜50秒で、現実的な尺度（case1の数秒は小網のせい）
- **8,000件/時、台数50〜200（`smat-sweep-2026-09-22.txt`）: レールの渋滞は起きていない**（渋滞係数1.01）。50〜100台で配送が遅いのは台数不足（車を待つ時間）で、150台で解消。この領域では内蔵の動的経路は静的より**悪い**（渋滞がないのに台数ペナルティで遠回り）
  - 静的: 50台 3,454件／p95 1,917s → 100台 6,981／458 → 150台 7,828／96 → 200台 7,820／93
  - 動的: 50台 3,128／2,060 → 100台 5,767／927 → 150台 7,804／122 → 200台 7,809／115
- 含意: 「増車が効かなくなる」領域は、この大きさのレイアウトではもっと高密度（数百〜千台、数万件/時）にある。IJPR 2020の実工場（160m×80m）は最大170台で渋滞したが、SMAT2022はその4倍の面積
- **30,000件/時、静的、台数400〜1,000（`smat_probe.sh` → `smat-probe-2026-09-22.txt`）: 増車が効かなくなる領域が出た**
  - 400台 21,679件（渋滞係数1.30、デッドロック0）→ 600台 19,033（1.86、9）→ 800台 11,238（2.98、25）→ 1,000台 2,837（1.88、53）
  - 台数を増やすほど完了件数が減る。現実の規模（1,000台）でB4の形。1本の実時間は44〜66秒
- 同条件の内蔵動的経路（`smat_dense.sh` → `smat-dense-2026-09-22.txt`。メモリ逼迫で1,000台と動的800台の軌跡は未実行）
  - 動的: 400台 15,522件（デッドロック32）→ 600台 18,804（48）→ 800台 15,511（45）
  - **低密度（400台）では動的の方が悪い**（静的21,679 vs 動的15,522。遠回りとデッドロック増）。高密度（800台）では動的の方が良い（11,238 vs 15,511）。600台は同等
  - 読み: 内蔵の「台数比例の固定重み」は、混んでいないときは害、混んだときだけ益。重みの決め方に原理がないことの現れで、Kooの「固定重みが低〜中負荷で学習重みに勝つ」とも整合。**提案手法が狙う場所はここ**（密度に応じて自動で重みが決まる）

## 乱数の種による再実行（2026-09-22）

需要20倍、1時間、要求28,384件。完了件数の平均（標準偏差）、n=5。

| 台数 | 固定経路 | 動的経路 |
|---|---|---|
| 25 | 28,359 (0) | 28,360 (0) |
| 50 | 28,332 (0) | 28,335 (0) |
| 100 | **3,402 (127)** | 28,297 (0) |
| 200 | 1,725 (79) | 1,471 (50) |
| 400 | 867 (47) | 946 (13) |

分かったこと:

1. **デッドロックが起きない条件では、種を変えても結果が完全に同じ**（標準偏差0）。原因は確認済み: 搬送要求は**等間隔**で発生させている（`cosim/fromto_amhs.py:103` 「Schedule fixed-interval (3600/rate s) events」、`common/fromto_parser.generate_fixed_interval_events`）。ポアソン到着ではないので、種は需要に効かない。先行論文（IJPR 2020）は指数分布の到着間隔を使っている。同条件比較のときは、要求生成をポアソンに差し替える必要がある（第1期の作業）
2. **デッドロックが起きる条件では、種で結果が変わる**（100台固定で3,161〜3,525）。前回の3,403と3,482の差はこれ。デッドロック解消の順序に乱数が入っている
3. 図に使う形: 固定経路は50→100台で崩壊（28,332→3,402）。動的経路は100台までは崩れず、200台で崩壊（28,297→1,471）。「増やすと崩れる」「動的経路は崩壊点を先へ延ばす」の2つが同じ図に出る。ただし1と、平均搬送時間が数秒という不審点が未解決なので、申請書には「公開シミュレータ上の予備実験、指標の妥当性は検証中」と明記する
4. 動的経路は1本80〜160秒（固定は5〜10秒）。経路コストのキャッシュ（TTL 5秒）で再探索が増えるため
- **下から見上げる60fps動画（9/23）**: `renders/oht-underview-smooth-60fps.mp4`（1920×1080、20秒）。占有ログの線形補間はカクつく（区間ごとの速度 p99 26 m/s、区間のつなぎ目で最大9 mの瞬間移動）ので、`build_microsim.py` で経路だけをログ（動的経路800台）から取り、動きを追従モデル（IDM、直線4.0 m/s・カーブ1.5 m/s、合流の譲り合い、分岐で抜けきるまで待つ）で60 Hzに計算し直す。カーブのレールはベジェで滑らかにする。密度は車両の50%（`--keep 0.5`）。積み下ろしはログに無いので合成（ベイを通る車の60%がロードポートでホイスト昇降、`--p_stop 0.6`）。描画は `viewer3d/make_traj_page.py` → `closeup-traj.html` を `render_underview.py --page closeup-traj.html` で1コマずつ撮る
  - 再現: `build_microsim.py --keep 0.5 --p_stop 0.6 --r0 922 --r1 942` → `render_underview.py --page closeup-traj.html --video OUT.mp4 --secs 20 --look 6 --ty 3.9 --path '{"start":[-5.0,-13],"dir":[0,1],"len":6,"side":[0,0]}'`
  - 検証: 最高速 4.02 m/s、1コマで0.4 m/s以上の速度変化 0件、車両どうしの最小間隔 0.94 m（並行する幹線どうし）
